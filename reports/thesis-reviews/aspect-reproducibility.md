# Reproducibility and artifact usability review

The thesis has a serious reproducibility infrastructure, particularly for the game-paper experiments, but the two empirical components are not equally auditable. The revised game study supplies configurations, individual-image scores, statistical aggregation and executable reproduction commands. The Hidden Monotonicity component retains published results without the corresponding ImageNet result inputs, and its documented MNIST training entry point lacks required configuration files. These are specific, repairable weaknesses in the evidence package. They are not grounds for dismissing the research, and the available artifacts do not establish that the reported numerical results are wrong.

This assessment uses the [master’s-thesis criteria](assessment-criteria.md). The thesis combines a CVPR 2026 Highlight and an arXiv preprint; publication recognition deserves credit but does not replace reproducibility of the integrated thesis. An excellent master’s thesis need not repeat a roughly 450 GPU-hour programme simply for examination. It should make the central results traceable, expose missing evidence, and demonstrate that a bounded reproduction route works.

## Scope and checks

The review examined the thesis’s experimental and audit appendices, repository documentation, table manifest and adapters, both pinned implementation repositories, sample result JSONs, and compressed individual-image score files. Both submodule revisions matched the manifest, with no local modifications reported. Their hashes are recorded in the [repository guide](../../README.md) and [table-source manifest](../../scripts/table_sources.json).

A fresh CPU reconstruction run coordinated during this review used `scripts/generate_thesis_tables.py --check` against game-code revision `9cae01ce429c34b295aa06dd056895ddd4ef9ff7`. The [retained run log](../evidence/tex-resumption/table-reproduction.log) and [exit status 0](../evidence/tex-resumption/table-reproduction.exit) report all 13 supported outputs matching the thesis, including table structure and row associations after presentation adaptation. The run did not evaluate a model or download a dataset. Earlier corresponding evidence is retained in [table-adapter-verification.json](../table-adapter-verification.json). This review did not install either complete evaluation environment from scratch, execute GPU experiments, or independently rerun the implementation test suite; those remain separate verification tasks.

## Substantial strengths

The game release goes well beyond publishing code or table means. Its [summary documentation](../../code/playing_backward/results_summary/README.md), lines 5–16, identifies row configurations, validation selections, runtime benchmarks and compressed individual-image scores used for confidence intervals and paired tests. Inspection found 565 distinct test-image identifiers for each ImageNet backbone. This enables an examiner to audit aggregation and statistical comparisons without repeating expensive attribution computation.

The [game reproduction guide](../../code/playing_backward/README.md), lines 61–75, maps validation grids, selection, test evaluation, confidence intervals, ablations, transfer, diagnostics and qualitative outputs to commands. It supports resumable and sharded runs, specifies checkpoint weight enums, and documents ImageNet access rather than pretending licensed images can simply be included in Git. The [dataset loader](../../code/playing_backward/data/imagenet_s.py), lines 63–75, explains the 752-mask starting pool, label-agreement filtering to 616 images, and subsequent validation/test division. The shipped label file and deterministic split logic are useful safeguards.

The thesis repository also distinguishes proof checking, implementation testing and empirical reproduction. The [audit appendix](../../tex/chapters/10_appendix.tex), lines 795–802, explicitly states that Lean does not certify the Python implementations or experiments. The table adapter compares canonical TeX structure as well as numerical content, refusing a numerical match with different row associations ([generator](../../scripts/generate_thesis_tables.py), lines 100–109). Its manifest names unavailable inputs rather than silently generating placeholders. These choices reflect good scientific judgment.

## Principal concerns

### Required training configurations are missing

This is a confirmed artifact defect. The [Hidden Monotonicity multi-seed guide](../../code/hidden_monotonicity/difference_of_networks/multi_seed/README.md), lines 9–15 and 25–35, lists six configuration JSONs and instructs the reader to run ten seeds. Neither that `configs/` directory nor those six files is present in the pinned checkout. The [runner](../../code/hidden_monotonicity/difference_of_networks/multi_seed/run_multi_seed.py), lines 39–45 and 242–246, loads that exact directory and returns when it finds no configurations. Thus the documented entry point cannot reproduce its training experiments as shipped, regardless of whether the reader has sufficient hardware. A static accuracy table is not a substitute for the missing training specifications.

**Must correct:** release the exact configurations and their relationship to the thesis’s model variants, or explicitly mark this route as incomplete. For a persuasive 1.0 case, retain per-seed summaries and execute one configuration as a documented smoke test. Completion means a new checkout discovers the advertised configurations, the smoke run produces the expected schema, and the published accuracy aggregation can be traced to individual seed results. This does not require retraining every model during review.

### Important empirical conclusions remain outside the released reconstruction path

The [manifest](../../scripts/table_sources.json), lines 11–13, explicitly records that the Hidden Monotonicity ImageNet result inputs and table generator are absent. Lines 94–117 identify six game outputs unavailable from the shipped summaries: diagnostic numbers, double randomization, input-noise baselines, individual-image correlations, pointing-game granularity and randomization checks. These concern substantive thesis claims, particularly the trajectory diagnostics, rather than peripheral illustrations.

The manuscript is honest that its experiments are inherited rather than rerun ([experimental chapter](../../tex/chapters/08_experiments.tex), line 3), so this is not a concealed reproduction claim. Nevertheless, readers cannot apply the same independent reaggregation standard to both core empirical contributions. **Needed for a persuasive 1.0 case:** recover and archive the scalar outputs, configurations and identifiers behind the principal split-method tables and central trajectory diagnostic. Where cached maps are necessary, provide a clearly specified regeneration route or an appropriately distributable subset. Completion means selected central results regenerate from an identified artifact release; unrecovered results remain explicitly classified as published-source evidence. Copyrighted input images need not be redistributed.

### The older evaluation environment is insufficiently fixed

The game release provides an evaluation `requirements-lock.txt`; the older release pins Torch and torchvision but allows broad ranges for much of the metric stack, including `quantus>=0.5.0` ([Hidden Monotonicity requirements](../../code/hidden_monotonicity/requirements.txt), lines 13–43). This matters scientifically: the [game requirements](../../code/playing_backward/requirements.txt), lines 23–25, explicitly explain that Quantus 0.5 and 0.6 differ in channel broadcasting and Pixel Flipping curve length. Installing a currently satisfiable environment therefore does not establish that the older metric semantics have been recovered.

This is an environment-provenance gap, not proof that the published tables used incorrect metrics. **Needed for a persuasive 1.0 case:** preserve the actual older evaluation environment, or document a validated reconstruction of it. Add a small fixed metric fixture checking the intended perturbation count, channel treatment, curve aggregation and score direction. Completion is agreement with an archived expected result under a documented tolerance, rather than merely successful imports.

### Reproduction guarantees need narrower wording

Two statements in the pinned game guide exceed the demonstrated scope. Lines 91–94 say the shipped summaries regenerate every result table, whereas its own [summary guide](../../code/playing_backward/results_summary/README.md), lines 23–26, excludes diagnostics. Lines 22–25 promise bit-exact reproduction from the environment lock. The [seed helper](../../code/playing_backward/reproduce/common.py), lines 644–656, seeds Python, NumPy and Torch and disables TF32, but does not itself enable deterministic algorithms. A package lock alone cannot establish a platform-independent numerical guarantee; PyTorch’s [reproducibility documentation](https://docs.pytorch.org/docs/2.15/notes/randomness.html) distinguishes control of random seeds from algorithm and platform determinism.

**Must correct the documentation:** describe exactly which tables reconstruct and promise agreement within stated tolerances unless bitwise identity has actually been tested. The thesis-level README already makes the first distinction correctly. A versioned correction or explicit caveat alongside the pinned upstream instructions is sufficient; silently changing the submodule would weaken provenance. Completion means the instructions and manifest agree, and a demonstrated reproduction tolerance is attached to a specified environment and hardware configuration.

### A bounded independent rerun would close the most important practical gap

The completed table reconstruction establishes faithful transformation of saved scores into reported tables. It does not test whether a clean installation, original inputs and released attribution code produce those scores. The detailed protocol, checkpoint URLs and reported hardware are valuable, but a reader still has to assemble that final link.

**Needed for a persuasive 1.0 case:** provide a small, explicitly designated reproduction target covering one central proposed method and one strong baseline for each campaign, plus one trajectory diagnostic. Record commands, code and environment identifiers, checkpoint hashes, exact sample identifiers, expected outputs, tolerances and observed deviations. A short smoke test should validate the installation; a selected full reported row should validate the empirical chain. These are different acceptance criteria. A complete rerun of every grid, architecture and expensive robustness row is optional strengthening, not the minimum demand.

## Overall assessment

The game component is substantially more inspectable than a typical “code available” release, and the successful 13-output reconstruction is meaningful evidence. The thesis also avoids conflating formal proof with experimental validation. Those strengths should receive serious credit in a master’s assessment.

The remaining weakness is uneven coverage, not lack of effort: the reader can audit the main game statistics but encounters missing training inputs, missing split-campaign scores and incomplete diagnostic artifacts elsewhere. A compelling 1.0 case would prioritize repairing those gaps and documenting one bounded independent reproduction over adding further models or theorems. With that work, the artifact package would support the thesis’s scientific ambition much more convincingly. Without it, the thesis may still contain excellent research, but a thesis-wide claim of exceptionally strong empirical reproducibility is not yet established.
