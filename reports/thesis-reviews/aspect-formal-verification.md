# Review of formal verification and proof evidence

The formalization is a substantial strength of this master's thesis. Its verification discipline is considerably more convincing than an unqualified claim that the mathematics “builds in Lean.” The principal weakness is accessibility: an examiner must cross-reference several machine-readable files to discover exactly which part of a displayed thesis statement has been checked. This is a presentation and evidence-management problem, not evidence that the proofs are unsound.

This review applies the [master's assessment framework](assessment-criteria.md). It examines the verification driver, exact-contract manifest, imported-environment audit, coverage and link metadata, formalization guide, appendix disclosure, and selected game definitions. It does not independently reprove the entire development. The completed release evidence examined here is the [clean receipt at source commit `0f3cfb0ea660556c14da510e665281f07acc471d`](../verification/commit-0f3cfb0/receipt.json): 139 modules, 370 exact declaration contracts, and 3,048 imported project theorem constants. All 140 recorded commands exited successfully, and the theorem axiom audit passed with only the allowed foundational axioms. This supersedes the earlier 125-module receipt for the integrated source closure. The separately reviewed six-leaf routing batch remains outside production and is not certified by this receipt.

## What deserves credit

The project has a coherent verification boundary. The [verification driver](../../formalization/scripts/verify.py), lines 47–60 and 138–146, hashes the imported source closure and bound configuration and compares their contents with a committed snapshot. It rejects omitted production modules, requires every linked declaration to have an exact contract, and checks that sources have not changed during the run. The retained commands, exit codes, generated driver, environment inventory, and hashes make a successful result inspectable rather than anecdotal.

The type checks also address a real failure mode in generated formalization. Expected propositions are elaborated in separate declarations before the target proof can constrain them; the checker then compares full types and verifies universe arity and defining module (`verify.py`, lines 88–107). The [environment audit](../../formalization/checks/environment_audit.lean), lines 11–24, inspects imported project theorem constants, including generated declarations, and restricts their axiom dependencies to `propext`, `Classical.choice`, and `Quot.sound`. These measures substantially reduce the risk of crediting an accidental specialization, a similarly named theorem, or a proof containing an admitted obligation.

The mathematical modelling is also more serious than a collection of disconnected algebraic examples. The [formalization guide](../../formalization/README.md), lines 9–47, describes shared varying-width network parameters, actual forward evaluators, extracted gates, affine readouts, and continuous linear derivatives. A limited inspection of the softplus game confirms that equilibrium is defined using actual local best-response inequalities and is obtained from arbitrary-policy bounds; it is not simply supplied as an assumed conclusion. See [SoftplusEquilibrium.lean](../../formalization/Thesis/SoftplusEquilibrium.lean), lines 64–91, and [SoftplusReadout.lean](../../formalization/Thesis/SoftplusReadout.lean), lines 65–77. This is a positive spot-check, not a certificate for every source correspondence.

Finally, the thesis already communicates important limits. [Appendix A, Formal Verification and Mathematical Audit](../../tex/chapters/10_appendix.tex), lines 735–745 and 795–802, calls the formalization partial and explicitly excludes certification of the Python implementations and experiments. Its distinction between selected backward quantities and classical derivatives is scientifically valuable. The recorded corrections show that the formalization has served as an audit of the mathematics, rather than merely decorating the manuscript with proof-assistant links.

## Principal concerns

### The scope of a numbered link is not visible where the reader needs it

The PDF uses the same `Lean_N` notation for a complete formal variant and for components of a broader theorem. The [link macro](../../tex/preamble/lean_links.tex), lines 5–18, stores the display description but renders only the number. Meanwhile, [README lines 153–155](../../formalization/README.md) still describe visible “Lean variant” and “Lean components” badges. That description is stale.

The appendix acknowledges the distinction, so this is not an accusation of concealed limitations. Nevertheless, the burden on the examiner is substantial. The [link metadata](../../formalization/tex_links.json) shows that routing recovery, fixed-attention recovery, and complete CNN assembly have different boundaries. For example, the attention result fixes a non-negative row-stochastic attention matrix and does not certify differentiation through Query/Key softmax or a global attention equilibrium. The CNN entry records shared-DAG components and a tensor-to-matrix bridge while leaving an assembled architecture/compiler bundle open. A uniform link beside a large theorem cannot communicate those differences.

**Needed for a persuasive 1.0 case:** add a concise, examiner-facing scope table for the central linked results. Preserve the requested numbered style, but identify the source statement, the checked model and assumptions, and the remaining parts. Include routing equilibrium versus occupation recovery, attention, randomization, CNN assembly, and smooth activations. **Done means:** a reader can determine the exact certification boundary of each central claim from the thesis itself; the README describes the actual rendering.

### Kernel checking cannot establish source correspondence or independent review

The verification mechanism proves that the implemented theorem has the recorded type and approved axiom dependencies. It cannot establish that the expected type was independently conceived, that a definition models the intended neural-network operation, or that a hypothesis has not absorbed the substantive research claim. The repository recognizes this distinction, and the [coverage map](../../formalization/coverage_map.json) is unusually explicit about it.

For instance, the routing equilibrium and the older alpha-beta recovery result use different trajectory encodings; their full identification remains a separate obligation in [README lines 108–115](../../formalization/README.md). The randomization entries distinguish conditional-kernel contraction assumptions from deriving those assumptions for concrete randomized weights. Those are useful mathematical results, but neither a larger axiom-audit count nor a successful build closes the missing bridge.

**Needed for a persuasive 1.0 case:** give two or three short worked correspondence explanations, showing how a central TeX statement becomes a Lean theorem and why each hypothesis is necessary. Include one difficult boundary, such as zero stabilizer, a pooling tie, or an affine readout. The author should explain the modelling and validation decisions, especially because the appendix discloses AI-assisted formalization. **Done means:** an examiner can follow the argument from the scientific claim to the actual objects and assumptions without relying on declaration names or total line counts. Completing every open formalization is not required.

### The semantic-review evidence and final release need an explicit connection

The [manifest](../../formalization/verification.json) contains review identifiers and evidence paths, and detailed adversarial reports are retained. However, `source_snapshot` binds the manifest and coverage map without hashing the referenced review-report files themselves. A stable manifest therefore identifies a review but does not, by itself, bind its precise content. This does not invalidate any kernel-checked theorem; it limits what the receipt alone establishes about the review chain.

**Recommended provenance improvement:** include the relevant semantic-review report hashes in a final release manifest. Tie the PDF's Lean URLs, the verified source commit, the exact-contract counts, and the scope summary to that same release. **Done means:** a fresh reader can identify the reviewed evidence for the published statements and distinguish it from subsequent development. The integrated source now has its own completed clean gate. The release check must still establish that the published PDF and its generated links point to that verified commit, and must not credit the separate unimported routing batch to this receipt.

## Consequences for experiments and the master's assessment

This formal work supports exact mathematical identities. It does not establish that floating-point implementations, stabilization thresholds, metric code, or generated tables implement those identities correctly. The appendix says this clearly, and that honesty should remain prominent. Implementation correspondence needs separate executable checks and experimental provenance; a formally verified compiler or a fully verified machine-learning stack would be disproportionate requirements for this degree.

On the inspected evidence, formal verification strengthens the case for an excellent thesis. The remaining priority is to make the central assurances legible and reproducible, not to maximize theorem counts. Neither the CVPR Highlight status of one component nor the volume of Lean code substitutes for an examiner's judgment of mathematical understanding, experimental rigor, and independent contribution. Conversely, the preprint status of the other component and the explicitly incomplete formalization are not grounds for downgrading otherwise sound work. A credible 1.0 case requires precise claims and accessible evidence, not proof-assistant coverage of every paragraph.
